# Security assessment

An audit of Veil against its own claims, including defects found in the
process. Written to be useful to someone deciding whether to trust it, which
means the findings section comes before the reassurance.

**Scope.** Static review of the whole codebase, plus the 283 automated tests,
plus targeted measurement (Argon2id timings, relay behaviour under real HTTP).
**Not** in scope: dynamic analysis on a device, fuzzing, side-channel
measurement, or review by anyone other than the author of the code. That last
point is the important one — see finding H-1.

---

## 1. Verdict

**Is it secure?** The cryptographic design is sound and conservatively built,
and the implementation matches the specification as far as review and testing
can establish. The Android platform hardening is better than most messengers
ship.

**Would I recommend relying on it today?** No — because of H-1 alone. Not
because a specific flaw is known, but because "no independent review" is itself
the finding that dominates all others in a cryptographic product.

**Does it ensure that messages can "never be accessed by anyone"?** No. No
system can, and any product claiming it is misleading you. See §4, which is the
most important section in this document.

---

## 2. Findings

Severity is about impact on the security claims, not about how hard the fix is.
Everything marked *fixed* was found and repaired during this review; the commit
history shows each one.

### High

**H-1 · No independent audit.** *Open. Unfixable from inside the project.*
The code is a careful implementation of well-specified constructions with
extensive negative testing. That is not equivalent to adversarial review by
people paid to break it. Cryptographic bugs are routinely subtle enough to
survive exactly this level of care — the history of the field is largely a
history of well-intentioned implementations failing in ways their authors could
not see. Everything else in this document is conditional on this.

**H-2 · Release builds were signed with the committed debug keystore.**
*Fixed.* The React Native template ships `signingConfig signingConfigs.debug`
inside the release block, beside a `debug.keystore` whose password is the
public, well-known `android`. Shipping that would let anyone produce a build the
platform accepts as a genuine update to this app — a complete compromise of
code integrity, from a default nobody has to touch to be caught by. Now driven
by `VEIL_KEYSTORE_*` environment variables, with the build failing rather than
falling back. Asserted by tests in `apps/mobile/test/androidConfig.test.ts`.

**H-3 · Ratchet state was mutated before a failure point.** *Fixed.*
`performDhRatchet` reset the send/receive counters and adopted the peer's new
ratchet key *before* performing the Diffie-Hellman agreement. X25519 rejects
degenerate public keys and the ratchet header is attacker-controlled, so one
injected frame with an all-zero key threw after the counters were clobbered,
leaving the session unrecoverable. Reachability was narrow (an established
session is required, so an attacker could only break their own conversation
with the victim) but it was a session-destroying bug from a single crafted
frame. All fallible work now happens before any mutation.

### Medium

**M-1 · The app requested `SYSTEM_ALERT_WINDOW` and storage permissions.**
*Fixed.* Pulled in transitively by `react-native-webrtc` and Expo modules.
`SYSTEM_ALERT_WINDOW` ("draw over other apps") is the basis of tapjacking and
has no business in a 1:1 voice app; the storage permissions expose data to any
other app holding the same permission. Both now stripped by
`plugins/withAndroidPrivacy.js`, with a test asserting the permission list is
exactly what the app needs.

**M-2 · The build referenced XML resources that did not exist.** *Fixed.*
The generated manifest pointed at `@xml/secure_store_backup_rules`, which was
absent — the release build would have failed on a missing resource. Now
generated by the plugin, with deny-everything content.

**M-3 · Argon2id parameters were ~5x more expensive than documented.**
*Fixed.* `SECURITY.md` claimed 64 MiB / t=3 cost "roughly 100-300 ms on a
mid-range phone". Measured: ~1620 ms on a 2.8 GHz x86 core under V8, and Hermes
on a phone is a small multiple slower again. Several seconds of blocked UI at
unlock risks an Android ANR, and an unlock that feels broken gets "fixed" by
cutting parameters to something far weaker or by users choosing short
passphrases. Moved to 46 MiB / t=2 (an OWASP-documented profile, ~780 ms
measured) and the claim corrected with the measurement methodology.

**M-4 · The keystore layer documented protections it did not implement.**
*Fixed.* The comment claimed `requireAuthentication` was one of "two options
that matter here" — the code never set it. It also implied
`keychainAccessible` protected Android, where that option is ignored entirely
(iOS-only). And `hasHardwareKeystore()` actually probed *biometric
availability*, which is a different question; no API reports whether the
keystore is hardware-backed, so the app must not claim that it is. Rewritten
with accurate platform-specific comments, a real capability probe, and
`requireAuthentication` requested when the device can honour it — with the
actual mode surfaced to the user rather than assumed.

**M-5 · No lock on backgrounding.** *Fixed.* An unlocked vault kept its data
key in memory indefinitely, so anyone picking up an unlocked phone read
everything. Now wiped after 30 s in the background, driven by elapsed time
rather than a timer (a suspended process may never run its timer). Fails closed
if the clock moves backwards.

**M-6 · Screenshots and the recents thumbnail were unprotected.** *Fixed.*
Android snapshots the visible screen when an app backgrounds; that image lands
outside the encrypted database. `FLAG_SECURE` is now set app-wide via
`expo-screen-capture`, and a failure to set it is surfaced to the user instead
of assumed to have worked.

**M-7 · R8 was enabled without keep rules, and cannot be verified here.**
*Partially fixed.* Minification is valuable (it strips debug metadata and raises
reverse-engineering cost) but R8 removes code it cannot see used, and React
Native, Expo and WebRTC all resolve native classes reflectively from
JavaScript. Conservative keep rules are now generated by
`plugins/withProguardRules.js` and asserted by tests. **This remains a residual
risk:** no Android SDK was available in this environment, so no APK was built
and the release configuration is unverified end to end. A release build must be
smoke-tested — install, register, send, call — before distribution.

### Low

**L-0 · Passphrase guessing was unthrottled.** *Fixed.* Argon2id makes each
guess cost ~1s, which defeats a fast offline attack on a copied database, but
it did nothing against someone holding the phone and trying passphrases by
hand — a few thousand attempts is a weekend. Now three free attempts (for
typos) then escalating lockouts to a five-minute cap. The counter is stored in
the platform keystore rather than the encrypted database: beside the data, an
attacker could copy the database, burn attempts, restore the copy and reset the
throttle. Parsing fails closed, so corrupting the counter imposes a lockout
rather than clearing it. Wipe-after-N is available but off by default — for a
personal two-person app with no backup, a pocket or a child should not be able
to destroy the only copy of a history.

**L-1 · Notification content is unimplemented, and is a trap.** *Open.*
`POST_NOTIFICATIONS` is declared but no notification code exists. The obvious
implementation puts the sender and a message preview in the notification, which
writes plaintext into the system notification database and onto the lock
screen. Whoever implements this must show a contentless notification
("New message") and nothing more.

**L-2 · Passphrases are JavaScript strings and cannot be wiped.** *Open.*
`wipe()` covers key buffers, but the passphrase passes through React state as
an immutable string. JS gives no way to zero it, and the GC may have copied it
already. Mitigated by the short window and by the passphrase never being
persisted; not eliminable without a native input path.

**L-3 · Ten-character minimum passphrase is weak against a determined
offline attacker.** *By design, documented.* Argon2id raises the per-guess
cost but cannot rescue a low-entropy secret. The real fix is binding the data
key to hardware (listed as outstanding work), so that offline attack requires
the device rather than just the database file.

**L-4 · Ten moderate advisories in the Android build toolchain.** *Accepted,
documented.* All from `expo → @expo/config-plugins → xcode → uuid@7`. That code
edits Xcode project files during `expo prebuild` on a developer machine; it is
never bundled, never runs on a device, and never touches key material. An npm
`overrides` pin is not honoured for that nested path by the installed npm. The
crypto core and the relay have **zero** advisories and CI gates on that at
`--audit-level=low`.

**L-5 · Certificate pinning is scaffolded but not enabled.** *By design.*
`veil_network_security_config.xml` denies cleartext and does not trust
user-installed CAs (which is what blocks a device-installed root certificate
from proxying the relay connection). A pin-set block is present but commented,
because a pin must match a specific deployment and a wrong pin bricks every
installed client. Note the limited benefit: message contents are already
end-to-end encrypted, so TLS interception reveals only the metadata the relay
sees anyway.

## 3. What held up under review

Stated so the assessment is not only a list of problems.

- **The handshake.** PQXDH with all four DH terms plus ML-KEM-1024, with the
  key identifiers and one-time-key presence flags bound into the transcript, so
  a prekey downgrade by the relay causes a decryption failure rather than a
  silent weakening. Tests confirm both sides agree, and that substituting the
  ephemeral key, the KEM ciphertext, or the claimed initiator identity all
  cause divergence.
- **Ratchet bounds.** Skipped-key derivation is capped per chain and in total,
  keys are consumed only on successful decryption (so a forged ciphertext
  cannot burn a real key), and state is committed only after the AEAD verifies.
- **Sealed sender.** The sender's proof is verified against the recipient's
  *locally computed* address, not the server-supplied routing field, so a relay
  that rewrites the destination gets a clean failure rather than an accepted
  message. Tests assert the relay's stored records contain no plaintext, no
  sender address, and no sender key, and that two messages from one sender are
  unlinkable.
- **Signature domain separation.** Identity bindings, signed prekeys, KEM
  prekeys, sender proofs and auth challenges are all signed under distinct
  context tags, so a signature from one context cannot be replayed into
  another. The same identity key serves all five, which is exactly when this
  matters.
- **Relay discipline.** No request logging (asserted behaviourally, and
  confirmed against a real running process), `trustProxy` off so
  `X-Forwarded-For` cannot be forged to evade rate limiting, hour-rounded
  timestamps, uniform responses that do not reveal whether an address is
  registered, challenges consumed even on failure, acknowledgement scoped to
  the caller's own queue.
- **Media encryption.** Directional SFrame keys bound to both identities and
  both DTLS fingerprints, installed before the call is reported connected, with
  nonce uniqueness enforced from both ends (the sender refuses to wrap at
  2^48; the receiver rejects replays and stale counters). The call is refused
  outright where frame encryption is unavailable.
- **The crypto boundary.** `primitives.ts` is the only file importing a
  cryptographic library, so every algorithm choice is reviewable in one screen.
- **The pairing lock.** Enforced before the session is stored and before the
  payload is interpreted, so refused traffic never touches ratchet state or the
  message store. Tests confirm a stranger's message creates no conversation, no
  contact and no history; that an unpaired device accepts nothing at all; that
  sending to a non-paired address is refused; and that re-pairing requires an
  explicit unpair, which deletes the history it could no longer decrypt.

## 4. "So nobody can ever access it" — the honest answer

This deserves to be stated plainly, because it is the expectation the whole
product is measured against.

**End-to-end encryption means the messages cannot be read in transit or by the
server. It does not mean nobody can ever read them.** The claim that anything
is permanently inaccessible to everyone is not achievable, and every messenger
that implies otherwise — including the commercial ones — is overselling.

What Veil genuinely prevents:

- the relay operator reading message content or hearing calls;
- the relay operator learning who sent a message, or building a sender-side
  social graph;
- anyone on the network reading content, now or after a future quantum break;
- a TURN/SFU relay hearing call audio;
- the platform backup service obtaining the message database;
- a thief with the locked device reading history.

What it cannot prevent, no matter how good the cryptography:

1. **The endpoints.** Plaintext exists on both phones — it has to, or the
   recipient could not read it. Anything with control of either device reads
   everything: spyware, a malicious keyboard, a compromised OS, a hostile app
   with accessibility permissions, or simply someone holding an unlocked phone.
   Commercial spyware attacks exactly this layer, precisely because the
   transport layer is solved.
2. **The other person.** They can screenshot (on their own device, if they
   modify the app), photograph the screen, forward the content, or show it to
   someone. No protocol constrains a legitimate recipient.
3. **You.** A forgotten passphrase, a coerced unlock, a shoulder-surfer.
   In many jurisdictions a court can compel a device unlock; the cryptography
   is irrelevant to that.
4. **Metadata.** The relay learns recipient addresses and connection IPs.
   Timing and volume leak. Sender anonymity is protected; anonymity is not.
5. **Traffic analysis.** An observer watching both users' connections can
   correlate them. There is no cover traffic.
6. **An unverified conversation** — *mitigated in paired mode.* If neither
   party ever compares safety numbers, an attacker who substitutes keys at
   first contact reads everything, and every other defence is bypassed. This
   was the most likely real-world failure. The two-person **paired mode** (now
   the default) closes it: pairing happens once in person via a code carrying
   the peer's signed identity, nothing the relay says is trusted, traffic from
   any other identity is discarded before decryption, and a key change is a
   hard stop rather than a dismissable prompt. What remains is that the users
   must actually exchange codes in person; if they paste a code from a channel
   an attacker controls, the attack works as before.
7. **Implementation bugs.** See H-1. Three real bugs were found in this
   codebase by its own author during this review. It is not reasonable to
   assume that is all of them.

The accurate claim is: *messages and calls are end-to-end encrypted, so the
operator and the network cannot read them, and recorded traffic stays
confidential even against a future quantum adversary.* Anything stronger than
that is marketing.

## 5. Recommendations, in order

1. **Get an independent cryptographic audit.** Nothing else on this list
   changes the verdict.
2. **Build and smoke-test a release APK.** The R8 configuration is unverified
   (M-7). Register, exchange messages, place a call.
3. **Bind the vault data key to the Android Keystore**, so an offline attack on
   the database requires the device rather than just the file. This is the
   single biggest improvement available to the at-rest story.
4. **Implement contentless notifications** before anyone implements
   notifications the obvious way (L-1).
5. **Reproducible builds and binary transparency.** Source availability says
   nothing about the binary a user installs.
6. **Blind-signed delivery tokens** for spam resistance without deanonymising
   senders.
7. **Enable certificate pinning** for your deployment, with a backup pin.
8. **QR verification flow**, since comparing a scanned code is the verification
   path non-technical users get right most often.
